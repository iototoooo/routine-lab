## 2. 分析の土台となるデータ
すでにある `occurrence_facts`（RLS が効く `security_invoker` のビュー、予定1回＝1行）に、集計に必要な列はほぼそろっている。

| 使う列 | 内容 |
| --- | --- |
| `planned_date`・`planned_weekday`・`time_band`・`planned_start_time_jst` | 予定日（JST）・曜日・時間帯 |
| `status`・`is_final` | 状態。`is_final` は完了・見送り・未実施だけ true |
| `postpone_count` | 延期した回数 |
| `actual_start_at`・`actual_duration_min`・`executed_date`・`is_late_day`・`start_source` | 有効な実績（修正前の行 `superseded_by` は除外済み） |
| `delay_min`・`duration_ratio` | 遅延（分）、所要時間の比 |
| `closing_reason_code` | 見送り・未実施の理由（最後のもの） |
| `routine_id`・`routine_version_id`・`version_no` | ルーティンと版（Phase 4 の比較用） |

**足りないもの（新しいマイグレーション1本で補う。適用は承認後）**
1. **テスト用ルーティンの印**：`routines.exclude_from_analytics boolean not null default false` と、切り替える RPC `set_routine_analytics(p_routine_id, p_exclude)`（`security definer`、`search_path = ''`、本人のルーティンだけ）。版（履歴）には入れない。印を変えると過去の分も含めて集計から外れる・戻るだけで、予定・実績は変わらない。
2. **延期の理由と選択肢を予定日で引けるビュー** `occurrence_reason_facts`（`security_invoker`）：`occurrence_events` のうち延期・見送り・未実施の行に、予定日・ルーティン・版を付けたもの。イベントの表には予定日がないので、期間で絞るために使う。
- 既存の表・ビュー・関数・トリガー・cron・通知は変えない。取り消し用 SQL（`supabase/rollback/2026XXXX_phase3_down.sql`）も作り、テストで確かめる。

## 3. 集計の決まり（「記録していない予定を完了にしない」）
| 予定の状態 | 達成率の分母 | 扱い |
| --- | --- | --- |
| 完了（`done`） | 入る（分子にも入る） | 延期してから完了したものも完了 |
| 見送り（`skipped`）・未実施（`missed`） | 入る | 延期してから見送り・未実施になったものも同じ |
| 予定どおり・通知済み・延期中（未確定） | **入らない** | 「未確定 N件」として別に表示する。完了とも失敗とも数えない |
| 取り消し（`cancelled`：アーカイブ・編集で無効になった予定） | 入らない | 表示もしない（件数だけ注記） |

- 未実施は「予定日の翌日の終わり」に確定するので、直近2日は未確定が多い。期間の最後に未確定があるときは「直近の予定は未確定を含みます」と出す。
- 件数が0の日・曜日は「0%」ではなく**データなし**（グラフでは棒を描かない）。
- 割合には常に件数を添える（例：「67%（2/3）参考値」）。**参考値は5件未満**（F-509）。マスごとに判定する。
- 中央値は件数が偶数なら中央2つの平均。表示は分単位で四捨五入。
- **テスト用ルーティン**（`exclude_from_analytics`）は既定で集計から外し、絞り込みで「テストも含める」を選んだときだけ入れる。

## 4. 分析指標
すべて `src/lib/analytics/` の純粋関数（入力：ビューの行の配列、出力：表示用の数値と件数）。画面から切り離して単体テストする。

| # | 分析 | 指標 | 内訳 |
| --- | --- | --- | --- |
| 1 | 日別・週別の達成率 | 達成率、完了・見送り・未実施・未確定の件数 | 日（予定日）、週（月曜始まり、JST） |
| 2 | 曜日別・時間帯別の傾向 | 達成率、件数、全体との差（ポイント） | 月〜日、6つの時間帯 |
| 3 | 予定開始と実際の開始の差 | 遅延の中央値・平均、±10分以内の割合、翌日以降の割合、分布（早め／±10分／10〜30分／30〜60分／60分超／翌日以降） | ルーティン・曜日・時間帯ごと。記録のしかた（`start_source`）ごとの件数 |
| 4 | 予定と実際の所要時間の差 | 比（実際÷予定）の中央値、差（分）の中央値、予定より長かった割合 | ルーティンごと |
| 5 | 延期 | 延期した予定の割合、1予定あたりの延期回数（0・1・2・3回以上）、選択肢の内訳（10分後〜明日）、理由の内訳、延期した予定の最終結果（完了・見送り・未実施の割合）、延期してから完了したときの遅延 | ルーティン・時間帯ごと |
| 6 | 見送り・未実施の原因 | 理由の内訳（7種類＋理由なし）、見送りと未実施の件数 | 種類ごと、曜日・時間帯との組み合わせ（件数の多いものだけ） |
| 7 | ルーティンごとの継続と変化 | 達成率、今の連続達成（確定した予定のうち完了が続いた回数）、最長の連続、直近4週と前の4週の差、週ごとの推移 | ルーティンごと（一覧表） |
| 8 | 設定変更前後の比較に向けた準備 | 版ごとの達成率・遅延・所要時間の比・件数、版の有効期間 | 版ごと（ルーティン詳細に表示）。Phase 4 で「同じ長さの期間」を切り出す関数 `windowAroundVersion` を用意する |

**記録のしかたと遅延（3）**：記録画面の「予定どおり」で完了すると、実際の開始＝予定時刻（遅延0分）として保存される（`start_source = 'planned'`）。本人が「予定どおりだった」と記録した値として遅延の集計に含め、内訳に件数を出し、「実測だけ」（今・タイマー・手入力）に切り替えて見られるようにする（判断事項3）。

**Phase 4 で使える形にすること**：提案ルール（R-01〜R-06）が使う値（遅延の中央値、曜日別の達成率と他の曜日の平均、所要時間の比の中央値、「時間がなかった」の割合、延期の割合と延期後の完了、週ごとの達成率）は、すべて上の関数の出力にそろえる。しきい値は Phase 4 で `thresholds.ts` にまとめる。

## 9. 判断していただきたいこと
| # | 内容 | 推奨 |
| --- | --- | --- |
| 1 | テスト用ルーティンの記録を、実際の達成率から外す方法 | **ルーティンに「分析に含めない」の印を付ける**（DB の列と RPC。端末をまたいで同じ結果になる）。代わりの案：名前の決まり（「テスト」を含むなど。誤判定の恐れ）、分析の開始日を決める（期間の前の記録をまとめて外せるが、その後に作ったテスト用は外れない） |
| 2 | 今ある「test」「テスト」の扱い | 公開後に画面で印を付ける（あなたの操作）。新しく作るテスト用も同じ |
| 3 | 「予定どおり」で記録した完了（遅延0分）を遅延の集計に含めるか | **含める**。件数を表示し、「実測だけ」に切り替えられるようにする |
| 4 | 週の区切り | **月曜始まり**（日付・曜日は JST） |
| 5 | 連続達成の数え方 | 確定した予定を予定日の順に並べ、**完了が続いた回数**（見送り・未実施で途切れる。未確定は飛ばす） |
| 6 | 未実施の理由 | Phase 3 では後から理由を付ける機能（F-407、Should）は作らず「理由なし」として数える。必要なら Phase 4 以降で追加 |

### 判断事項の結論（2026-11-08 承認）
1. テスト用ルーティンは「分析に含めない」の印（DB の列と RPC）で除外する。
2. 既存の「test」「テスト」は、公開後にユーザーが画面から除外する。
3. 「予定どおり」の完了は遅延0分として集計に含める。実測とは区別し、実測・時刻指定の記録だけに絞った分析もできるようにする。
4. 週は月曜始まり。
5. 連続達成は予定された回数で数える。予定のない日は失敗としない。見送り・未実施で途切れ、未確定は飛ばす。
6. 未実施の理由の後日入力は Phase 3 では作らない。

- 取得は「期間ごと」ではなく、本人の記録を全件（1000 行ずつ）読んでブラウザで絞る。連続達成と「直近4週と前の4週」を、選んだ期間に関係なく正しく出すため。1年・5ルーティンでも約1,800行。
