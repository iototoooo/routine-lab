## 2. 改善提案のルール（要件 6.2）
### 2.1 共通の決まり
- **対象**：アーカイブしていない、テスト用でない（`exclude_from_analytics = false`）ルーティン。
- **期間**：昨日までの直近 28 日（JST の予定日）。今日の予定は確定していないことが多いため入れない。
- **今の版のデータだけを使う**：期間内でも、今の版（`valid_to is null`）の予定だけを数える。版を変えたら、古い版の記録で同じ提案が出続けないようにするため（変えた直後は件数が足りず、提案は出ない）。
- **件数**：確定した予定（完了・見送り・未実施）が 5 件以上のときだけ判定する。ルールごとの件数の条件は下の表。
- **集計は Phase 3 と同じ定義**：達成率の分母は完了・見送り・未実施。遅れは「予定どおり」で入れた記録（入力上の 0 分）を除き、実測・時刻指定だけで計算する（判断事項 2）。翌日以降に実施した記録は遅れの計算から外す（24 時間以上の遅れで開始時刻を動かさないため）。
- しきい値は `src/lib/suggestions/thresholds.ts` に定数でまとめる。

### 2.2 ルール
| ルール | 条件 | 提案（変更後の設定） | 件数の条件 |
| --- | --- | --- | --- |
| **R-01** 慢性的な遅れ | 遅れの中央値が +20 分以上 | 開始時刻を中央値の分だけ遅らせる（15 分単位に丸める）。日付をまたぐ（24:00 を超える）場合は提案しない | 遅れを計算できる記録 5 件以上 |
| **R-02** 特定の曜日の不調 | ある曜日の達成率が 40% 未満で、ほかの曜日の平均より 30 ポイント以上低い | その曜日を外す。曜日が 1 つだけのルーティンには出さない | ルーティン全体で確定 5 件以上、その曜日で確定 3 件以上（判断事項 3）。少ない件数による傾向なので「参考傾向」と明示し、その曜日とほかの曜日の両方の件数を表示する |
| **R-03** 所要時間の不足 | 実際の所要時間 ÷ 予定の所要時間 の中央値が 1.3 以上 | 予定の所要時間を、実際の所要時間の中央値に合わせる（5 分単位に切り上げ、480 分まで） | 所要時間のある完了 5 件以上 |
| R-04 時間不足による延期・見送り | 延期・見送り・未実施の理由のうち「時間がなかった」が半数以上 | 所要時間を 2/3 に（5 分単位、5 分以上） | 理由のある記録 5 件以上 |
| R-05 延期の常態化 | 延期した予定が 50% 以上で、延期した予定の過半数が完了 | 開始時刻を、延期後に実際に始めた時刻の中央値に合わせる（15 分単位） | 確定 5 件以上 |
| R-06 安定して達成 | 直近 4 週それぞれで達成率 90% 以上 | 設定は変えない（「この調子」と表示するだけ。承認・却下のボタンなし） | 各週に確定 1 件以上 |

- R-04〜R-06 は今回作るかどうかを判断事項 1 で決める。
- 根拠として保存する値：ルール ID、期間（開始日・終了日）、件数、主な数値（中央値・達成率など）、今の版の ID と設定、提案の設定。

### 2.3 却下と重複の扱い
- **却下の効き目**：同じルーティン・同じルールの提案を、却下から 28 日間は出さない（提案の値が少し変わっても出さない。判断事項 4）。
- **承認の後**：版が変わるので、古い版のデータに基づく提案は自然に消える（2.1 の「今の版だけ」）。
- **1 つのルーティンに複数の提案**：同時に表示する。どれかを承認すると今の版が変わり、残りは消える（確認画面で今の版と照合する。3.2）。
- 提案は画面を開いたときに計算する（要件 6.2）。保存するのは承認・却下したときだけ。

## 3. データと RPC（新しいマイグレーション 1 本。適用は承認後）
### 3.1 表 `suggestions`
| 列 | 内容 |
| --- | --- |
| `id` uuid, `user_id` uuid, `routine_id` uuid | 本人のルーティン（外部キー `(routine_id, user_id)`） |
| `rule_id` text | `R-01`〜`R-06`（check 制約） |
| `base_version_id` uuid | 提案のもとになった版 |
| `evidence` jsonb | 根拠（期間・件数・数値） |
| `current` jsonb / `proposed` jsonb | 変更前と変更後の設定（曜日・開始時刻・所要時間・再通知） |
| `status` text | `accepted` / `rejected`（要件の `proposed` / `expired` は、表示時に計算するため使わない） |
| `decided_at` timestamptz, `applied_version_id` uuid（承認時だけ） | 判断の時刻と、承認で作った版 |

- RLS を有効にし、本人の SELECT だけ許可。INSERT / UPDATE / DELETE は RPC だけ（表の権限を `revoke`）。作成後は変更しない（`routine_versions` と同じ守りのトリガー）。
- `routine_versions.suggestion_id` に、この表への外部キーを付ける（Phase 1 で「Phase 4 で付ける」とした列）。

### 3.2 RPC
| 関数 | 内容 |
| --- | --- |
| `accept_suggestion(p_routine_id, p_rule_id, p_base_version_id, p_evidence, p_proposed, p_valid_from, p_change_reason)` | 本人のルーティンで、アーカイブされておらず、`p_base_version_id` が**今の版のままであること**を確かめる（違えば `stale_suggestion`）。28 日以内に同じルールを却下していないことも確かめる。`suggestions` に accepted を記録し、版の追加は既存の編集と同じ処理で行う（`source = 'suggestion'`・`suggestion_id` 付き）。作った版の ID を返す |
| `reject_suggestion(p_routine_id, p_rule_id, p_base_version_id, p_evidence, p_proposed)` | 本人のルーティンであることを確かめ、rejected を記録する。版・予定・通知には触れない |

- **既存の編集処理の扱い**：版は作成後に変更できない（トリガー）ため、`source` と `suggestion_id` は作るときに入れる必要がある。`_edit_routine` の本体を、`source` と `suggestion_id` を受け取る内部関数に移し、今の `_edit_routine` はそれを `manual` で呼ぶだけにする（`edit_routine` の引数・動きは変えない。既存の DB テストで確認）。
- 版を変えたときの予定・通知の付け直しは、手動の編集とまったく同じ（Phase 2 のトリガー）。新しい送信経路は作らない。
- 根拠（`evidence`）は画面で計算した値で、DB では再計算しない（本人のデータを本人が判断する記録のため）。DB では提案の設定の範囲（曜日・時刻・所要時間）と、今の版との照合だけを守る。
- 内部関数は `p_user`・`p_now` を受け取り、`security definer`・`search_path = ''`。外から呼べるのは authenticated だけ。
### 3.3 承認した提案を取り消したいとき
- 承認で作った版・`suggestions` の記録は消さない（要件 P-01・P-03）。元に戻すときは、**元の設定で新しい版を作る**（版 1 → 版 2（提案）→ 版 3（元の設定）。履歴に 3 つとも残る）。
- 画面：版の履歴で、提案から作った版に「この変更を取り消す（元の設定に戻す）」を置く。押すとルーティン編集画面が、提案の前の版の設定・変更理由「提案 R-01 の取り消し」を入れた状態で開き、ふだんの編集と同じ確認を経て保存する（`source = 'manual'`。新しい DB 関数は作らない）。
- 取り消した後も、同じルールの提案は承認の日から 28 日間は出さない（却下と同じ扱い。すぐに同じ提案が出て繰り返さないため）。
- Phase 4 の DB の変更そのものを本番から外すときは、取り消し用 SQL（下記）を承認後に使う。これは機能ごと外す非常用で、ふだんの「元に戻す」とは別。

### 3.4 取り消し用 SQL など
- 取り消し用 SQL（`supabase/rollback/20261110_phase4_down.sql`、判断記録・提案から作った版があれば止まる。11 章）と、本番スモーク（`supabase/tests/phase4_smoke.sql`、最後に必ず例外で全体を取り消す）を作る。

## 4. 画面
タブは今の 4 つ（今日・ルーティン・分析・設定）のまま。要件 5 章の画面遷移どおり、分析から提案へ進む。

| 画面 | パス | 内容 |
| --- | --- | --- |
| S-08 改善提案 | `/suggestions/` | 提案のカード（ルーティン名・ルールの説明・根拠・今の設定 → 提案の設定）。ボタンは「内容を確認する」と「却下する」（却下は確認ダイアログ）。提案がないときは「今は提案はありません」と、提案に必要な件数の目安。下に「判断の記録」（承認・却下の一覧） |
| 確認画面 | `/suggestions/confirm/?r=<ルーティン>&rule=<R-01>` | 開いた時点で計算し直し、変更前と変更後を並べる（ルーティン編集の確認と同じ見た目）。適用開始日（既定は判断事項 5）、変更理由（既定「提案 R-01：開始の遅れ（中央値 +25分）」、変更可）。「承認して新しい版を作る」。データや版が変わって提案がなくなっていれば、その旨を表示 |
| S-09 変更前後の比較 | `/routines/compare/?id=<ルーティン>&a=<版>&b=<版>` | 2 つの版を選ぶ（既定は 1 つ前と今）。前の版の最後の N 日と後の版の最初の N 日（N は最大 28 日、両方にある日数にそろえる）で、達成率・遅れ（中央値・±10分以内の割合・翌日以降の割合）・所要時間の比・理由の内訳を並べる。件数・期間・「参考値」・「同じ日数で比べられるのは N 日だけ」などの注意を表示。数値の表を必ず添える |
| 入口 | 分析画面・ルーティン詳細 | 分析画面の上に「改善提案 n 件」。ルーティン詳細に「このルーティンへの提案」「版を選んで比べる」。版の履歴に「きっかけ：提案（R-01）」 |
| 書き出し | 設定画面 | 「データを書き出す（JSON）」「予定と実績を書き出す（CSV）」 |

- `useSearchParams()` を使う画面は `<Suspense>` で包む。動的ルートは使わない（静的出力の決まり）。
- 確認画面と比較画面は `scripts/check-out.mjs` の確認対象に加える。

## 5. データの書き出し（F-801）
- **JSON**：本人のプロフィール・ルーティン・版・予定・実績（修正前の行も含む）・イベント・改善提案の判断・通知ジョブと送信結果。**端末の購読情報（endpoint・鍵）は入れない**（件数だけ）。テスト送信の記録も入れない。
- **CSV**：予定 1 回 ＝ 1 行（`occurrence_facts` と同じ列。日時は JST の表記と UTC の ISO 形式を両方）。Excel で文字化けしないよう UTF-8（BOM 付き）。値に `,` `"` 改行があれば引用符で囲む。
- 1000 行ずつ読み、画面側でファイルを作る。ファイル名は `routine-lab-YYYYMMDD.json` など。
- **iPhone のホーム画面アプリでの保存**：通常のダウンロードがうまく動かない場合があるため、共有シート（`navigator.share` でファイルを渡す）を使い、使えなければダウンロードにする。実機で確かめる。

## 8. 外部への影響と注意
- 承認で版が変わると、手動の編集と同じく、適用開始日以降のまだ通知していない予定の時刻と通知が付け直される。Phase 2 で実機未検証の「編集による時刻変更と通知の付け直し」を、ここで確かめられる可能性がある（別の項目として扱い、確認できたときだけ記録する）。
- **本番の記録はまだ少ない**（2026-11-09 時点で確定 5 件、実績 3 件）。今の版で 5 件以上の確定が必要なため、本番で提案が出るのは早くても数日〜数週間後になる。本番に架空の記録を入れて提案を出すことはしない（判断事項 6）。

### 判断事項の結論（2026-11-09 承認）
1. ルール：**R-01・R-02・R-03** の 3 種類（R-04〜R-06 は作らない）。
2. 遅れ：実測・時刻指定の記録だけ。「予定どおり」（入力上の0分）と翌日以降の実施は判定から除く。
3. R-02：ルーティン全体で確定 5 件以上・その曜日で 3 件以上。必ず「参考傾向」と表示し、その曜日とほかの曜日の件数を示す。外す曜日でなくなる予定日を承認前に示す。
4. 却下・承認の後：同じルーティン・同じルールは判断日から 28 日間出さない。手動の編集は制限しない。
5. 適用開始日：既定は明日。確認画面で変更できる。版の追加と予定・通知の付け直しは Phase 1・2 の仕組みをそのまま使う。
6. 提案 2 種類以上の確認：本番 DB に架空の記録を入れない。単体・DB・ブラウザテストで確認し、本番では記録がたまって提案が出たら実機で確認する。
7. 書き出し：JSON と CSV。ログイン情報・通知先の端末の情報と鍵・Secrets は含めない。本人の記録だけ。

## 11. 取り消し SQL の修正（2026-11-09、本番適用前の確認で発見・本番には未接続）
### 問題と原因
- 本番適用の事前確認（項目 9）で、提案を承認した後に取り消し SQL を実行すると、エラーなしで終わるが次の2つが起きることを手元の DB で確かめた。
  1. **履歴の食い違い**：判断記録の表（`suggestions`）を消す一方、提案から作った版は `source = 'suggestion'`・`suggestion_id` を持ったまま残る（消えた記録を指す。設定を変えた根拠・承認日時も失われる）。
  2. **再適用できない**：その状態で Phase 4 のマイグレーションを適用し直すと、外部キー `routine_versions_suggestion_fk` の違反で止まる。
- 原因：取り消し SQL が「判断記録がない状態」だけを前提にしており、記録がある場合の扱いを決めていなかった（元のテストは取り消しが通ることだけを確かめ、再適用を確かめていなかった）。
- この時点で本番の Phase 4 は未適用で、本番 DB には接続していない。

### 修正内容（案A、2026-11-09 承認）
- `supabase/rollback/20261110_phase4_down.sql` の最初（`begin` の直後、削除・変更より前）に安全チェックを追加：
  - 判断記録が1件以上、または提案から作った版（`source = 'suggestion'` または `suggestion_id` あり）が1件以上あれば、`PHASE4_ROLLBACK_REFUSED: 改善提案の判断記録 n 件・提案から作った版 m 件があるため、取り消しを中止しました（何も変更していません）` で止まる。
  - 止まったときはトランザクションが失敗状態になり、何も変わらない。両方 0 件のときだけ、今までどおり Phase 3 の状態に完全に戻す。
- 記録がある状態で戻す必要が出たときは、この SQL は使わず、改めて手順を相談する（先に JSON で書き出して保存する、など）。
- マイグレーション本体（`20261110000000_phase4_suggestions.sql`、md5 603d75c0…）とスモーク SQL（28dad6fd…）は変更していない。取り消し SQL は 2e9b5fdb…。
