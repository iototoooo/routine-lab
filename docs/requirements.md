## 1. 目的と概要

### 1.1 目的
曜日ごとのルーティンを登録し、**予定と実績の差** を記録・分析する。その結果をもとに、PDCA を回して自分に合ったルーティンへ改善していく Web アプリを作る。

### 1.2 PDCA との対応
| 段階 | アプリでの機能 |
| --- | --- |
| Plan（計画） | ルーティンの登録・編集。曜日・開始時刻・所要時間を決める |
| Do（実行） | 通知を受けて、完了・延期・見送りを記録する。実際の開始時刻と所要時間も残す |
| Check（評価） | 達成率と遅延の傾向を、日別・曜日別・時間帯別に分析する |
| Act（改善） | ルールに基づく改善提案。ユーザーが承認したときだけ設定を変え、変更前後の達成率を比べる |

### 1.3 利用者
- 主な利用者は開発者本人（1人）。認証とアクセス制御は、複数ユーザーでも安全に使える設計にする。
- 主な利用端末はスマートフォン（iPhone・Android）。ホーム画面に追加した PWA として使う。PC のブラウザでも分析画面などを閲覧できるようにする。

## 2. 設計の基本原則

| ID | 原則 | 内容 |
| --- | --- | --- |
| P-01 | 履歴を上書きしない | ルーティンを編集しても、過去の予定と実績は変えない。設定は **版（バージョン）** として追加し、各予定には作成時点の設定を写して保存する |
| P-02 | 3種類の時刻を区別する | **予定時刻**（いつやる予定か）、**通知時刻**（初回通知・再通知をいつ送るか）、**実行時刻**（実際にいつ始め、いつ終えたか）を別々の項目で保存する |
| P-03 | 失敗も記録する | 未達成・見送り・延期・遅延も、改善に必要なデータとして残す。削除しない |
| P-04 | 提案は自動で反映しない | 改善提案は、ユーザーが承認したときだけ新しい版として反映する。却下した提案も記録する |
| P-05 | 日本時間を基準にする | 日付と曜日は Asia/Tokyo で判定する。時刻そのものは UTC の timestamptz で保存する |
| P-06 | アクセス制御は DB で守る | 画面側のチェックに頼らず、Supabase の RLS で「本人のデータだけ」に制限する |
| P-07 | 無料枠で運用する | 有料の AI API・有料プランは使わない。無料枠の上限を超えない設計にする |
| P-08 | 静的出力を前提にする | 前回の課題で、Next.js の一部機能と静的出力・Cloudflare の相性問題が起きた。最初から静的出力で動く構成に限定する（7章） |

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| ルーティン（routine） | 「朝のストレッチ」など、繰り返し行う行動そのもの。名前などの基本情報を持つ |
| 版（routine version） | ルーティンの設定（曜日・開始時刻・所要時間・再通知）の1つの版。編集するたびに新しい版を追加し、古い版は有効期間を閉じて残す |
| 予定（occurrence） | 特定の日に行う予定の1回分。例：「2026-11-10（火）7:00 朝のストレッチ 15分」。作成時の版の設定を写して持つ |
| 実績（execution） | 予定に対して実際に行った記録。実際の開始時刻・終了時刻・所要時間 |
| 延期（postpone） | その予定を後で行うことにし、再通知の時刻を決めること。予定時刻そのものは変えない |
| 見送り（skip） | その回は行わないと、ユーザーが自分で決めること |
| 未実施（missed） | 期限までに、完了も見送りも記録されなかった状態。システムが自動で確定する |
| 遅延 | 予定開始時刻と実際の開始時刻の差（分） |
| 予定日 | 予定の日付（JST）。翌日に実行しても、予定日は変わらない |

### 4.2 ルーティン管理（主要機能1・2・12）
| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-101 | ルーティンの登録：名前（必須、40文字以内）、メモ（任意）、実施曜日（複数選択、1つ以上）、予定開始時刻（5分単位）、予定所要時間（5〜480分）、再通知の既定値（例：10分後） | Must |
| F-102 | ルーティンの編集：保存すると **新しい版** を追加する。適用開始日（既定は今日）と、変更理由（任意）を入力する。前の版は有効期間を閉じて残す | Must |
| F-103 | ルーティンの削除：**アーカイブ（論理削除）** とする。以後の予定は作らず、通知待ちの通知は取り消す。過去の予定・実績・版は残し、分析に使える | Must |
| F-104 | アーカイブしたルーティンの一覧表示と復元 | Should |
| F-105 | 変更履歴の表示：版ごとに、設定・有効期間・変更理由・変更のきっかけ（手動か提案か）を一覧で見られる | Must |
| F-106 | 一時停止（旅行中など、期間を決めて予定を作らない） | Could |

**編集時のルール**
- 適用開始日より前の予定は、一切変更しない。
- 適用開始日以降に作成済みの予定のうち、まだ通知も記録もされていないものは、作り直して新しい版に合わせる。通知済みや記録済みの予定は、そのまま残す。
- 1つのルーティンは、1日に1回とする。1日に複数回行う場合は、別のルーティンとして登録する。

| F-202 | 予定の作成は何度実行しても重複しない（ルーティン×予定日で一意） | Must |
| F-203 | 予定には、作成時の版のID、予定開始時刻、予定所要時間を写して保存する | Must |

| No | 画面 | パス（案） | 主な内容 |
| --- | --- | --- | --- |
| S-01 | ログイン | `/login` | メールアドレス入力 → 6桁コード入力 |
| S-02 | 今日 | `/` | 今日の予定を時刻順に表示し、状態（未通知・通知済み・延期中・完了・見送り）を示す。前日の未記録の予定、すぐ記録するボタン |

| S-06 | ルーティン詳細 | `/routines/detail?id=<ID>` | 版の履歴、過去の予定と実績、簡単な集計、版どうしの比較（S-09 へ） |

| S-08 | 改善提案 | `/suggestions` | 提案の一覧、根拠、承認・却下 |

- 静的出力では、`/routines/[id]` のような動的なパスは使いにくい（ビルド時にIDが決まらないため）。そのため、IDは **クエリ文字列** で渡す（7.2 節）。
- スマートフォンでは、画面下にタブ（今日・ルーティン・分析・設定）を置く。

### 主な画面遷移
```
通知をタップ ──→ S-03 記録 ──（完了・延期・見送り）──→ S-02 今日
S-02 今日 ⇄ S-04 一覧 → S-05 編集 / S-06 詳細 → S-09 比較
S-07 分析 → S-08 改善提案 →（承認）→ 変更内容の確認 → 新しい版を作成
```

## 6. データ・通知・分析の要件

### 6.1 データ構造（案）
すべての表に `user_id`（auth.users の ID）を持たせ、RLS で本人の行だけに制限する。

| 表 | 主な列 | 説明 |
| --- | --- | --- |
| `profiles` | user_id, timezone（既定 `Asia/Tokyo`）, default_snooze_min, quiet_hours | 利用者ごとの設定 |
| `routines` | id, user_id, name, note, archived_at, created_at | ルーティンの基本情報。削除は archived_at で行う |
| `routine_versions` | id, routine_id, version_no, weekdays（ISO 1=月〜7=日の配列）, start_time（time）, duration_min, snooze_min, valid_from（date）, valid_to（date, null=現在）, change_reason, source（`manual` / `suggestion`）, suggestion_id, created_at | **作成後は変更しない**。同じルーティンで有効期間が重ならないようにする |
| `occurrences` | id, user_id, routine_id, routine_version_id, planned_date（date, JST）, planned_start_at（timestamptz）, planned_duration_min, status（`scheduled` / `notified` / `postponed` / `done` / `skipped` / `missed` / `cancelled`）, next_remind_at, closed_at | 予定1回分。**一意制約：(routine_id, planned_date)** |
| `executions` | id, occurrence_id, actual_start_at, actual_end_at, actual_duration_min, executed_date（JST）, is_late_day（予定日より後の日に実施）, recorded_at, superseded_by | 実績。修正するときは新しい行を作り、古い行に superseded_by を付けて残す |
| `occurrence_events` | id, occurrence_id, type（`notified` / `postponed` / `skipped` / `done` / `missed` / `edited`）, remind_at, reason_code, reason_text, created_at | 状態の変化をすべて記録する（延期の履歴・理由を含む） |
| `push_subscriptions` | id, user_id, endpoint（一意）, p256dh, auth, user_agent, created_at, last_success_at, disabled_at | 通知を送る端末 |
| `notification_jobs` | id, user_id, occurrence_id, kind（`initial` / `snooze`）, fire_at, status（`pending` / `sending` / `sent` / `failed` / `expired` / `cancelled`）, attempts, sent_at, last_error | 送る予定の通知。**一意制約：(occurrence_id, kind, fire_at)** |
| `suggestions` | id, user_id, routine_id, rule_id, evidence（jsonb）, proposed（jsonb：変更後の設定）, status（`proposed` / `accepted` / `rejected` / `expired`）, decided_at, applied_version_id | 改善提案と、その判断の結果 |

**時刻と日付の扱い**
- 日時はすべて `timestamptz`（UTC）で保存する。画面への表示と、日付・曜日の判定は Asia/Tokyo で行う（日本はサマータイムがないため、変換は常に +9 時間）。
- `planned_date` と `executed_date` は JST の日付として保存する。予定日の翌日以降に実施したかどうかは、`executed_date > planned_date` で判定する。
- 深夜 0:00 をまたぐ予定（例：23:30 開始で 60 分）の予定日は、開始時刻の日付とする。

### 6.2 分析・改善提案のルール（案）
分析は SQL のビュー（RLS が効く `security_invoker`）か、取得したデータを画面側の TypeScript で集計する。どちらにするかは Plan Mode で決める。ルールは、テストしやすいように UI から切り離した純粋な関数にする。

| ルールID | 条件（直近4週、対象の件数5件以上） | 提案 |
| --- | --- | --- |
| R-01 慢性的な遅れ | 遅延の中央値が +20分以上 | 開始時刻を、遅延の中央値の分だけ遅らせる（15分単位に丸める） |
| R-02 特定の曜日の不調 | ある曜日の達成率が40%未満で、ほかの曜日の平均より30ポイント以上低い | その曜日を外す、または時刻を変える |
| R-03 所要時間の不足 | 実際の所要時間が、予定の1.3倍以上（中央値） | 予定所要時間を実績の中央値に合わせる |
| R-04 時間不足による延期・見送り | 延期・見送り・未実施のうち、「時間がなかった」が半数以上 | 所要時間を短くする（例：2/3）、または時間帯を変える |
| R-05 延期の常態化 | 延期の割合が50%以上で、延期後の完了が多い | 開始時刻を、延期後に実際に始めた時刻に合わせる |
| R-06 安定して達成 | 達成率90%以上が4週続いている | 現状を維持（必要なら負荷を上げる候補として表示するだけ） |

- 提案は、画面を開いたときに計算して表示する。承認・却下したときに `suggestions` に保存する。
- しきい値は定数にまとめ、あとで調整できるようにする。

### 6.3 通知の仕組み（案）
```
[毎日 0:00 JST] pg_cron ─→ 今日と明日の予定と notification_jobs を作る（SQL 関数、重複しない）
[毎分]          pg_cron ─→ 送信処理（Edge Function または Worker）を呼ぶ
                             ├ fire_at を過ぎた pending のジョブを取り出す
                             │   （FOR UPDATE SKIP LOCKED で sending にし、二重送信を防ぐ）
                             ├ 予定時刻から60分を過ぎていれば expired にする
                             ├ 本人のすべての有効な端末へ Web Push（VAPID）を送る
                             └ sent / failed を記録し、404・410 の端末を無効にする
[毎日 0:05 JST] pg_cron ─→ 前日分までの未記録の予定を missed にする（F-406）
```
- 延期すると `notification_jobs` に `snooze` のジョブを追加する。完了・見送りにすると、まだ送っていないジョブを取り消す。
- 通知の文面にはルーティン名を含める。通知の中身は暗号化されて送られるが、端末のロック画面には表示される。そのため、ロック画面での表示に注意するよう、設定画面で案内する。

## 7. 技術構成と制約

### 7.1 推奨構成
| 分類 | 技術 | 理由 |
| --- | --- | --- |
| フロントエンド | Next.js（App Router）＋ React ＋ TypeScript ＋ Tailwind CSS | 課題の方針どおり |
| 出力方式 | **静的エクスポート**（`output: "export"`） | Cloudflare Pages に置くだけで動く。サーバーのランタイムの相性問題を避けられる |
| 公開 | Cloudflare Pages（無料） | 前回の課題で実績あり。GitHub への push で自動デプロイ |
| 認証・DB | Supabase（Auth・Postgres・RLS）。画面からは supabase-js で直接読み書きする | サーバーを持たずに、RLS で安全にデータへアクセスできる |
| 定期実行 | Supabase の pg_cron（＋ pg_net） | 毎分の実行が可能。DB の中で予定と通知ジョブを作れる |
| 通知の送信 | **第1案：Supabase Edge Function**（pg_cron から毎分呼ぶ）。**第2案：Cloudflare Workers の Cron Trigger** | 送信には VAPID の署名とペイロードの暗号化が必要。Workers の無料枠は CPU 時間が 10ms と短いため、第1案を優先する。どちらにするかは Plan Mode で検証して決める |
| PWA | Web App Manifest ＋ Service Worker（`public/sw.js` を自作） | push を受け取り、通知のタップで画面を開くため。新しいパッケージは必要最小限にする |
| テスト | 純粋関数（日付・曜日・集計・提案ルール）の単体テスト、ブラウザでの画面テスト | 日付をまたぐ処理を確実にするため |

### 7.2 静的出力で使えない機能と、その代わり（前回の教訓）
| 使えない機能 | 代わりの方法 |
| --- | --- |
| Server Actions・Route Handlers（リクエストを読むもの）・Proxy（Middleware） | 画面から supabase-js で直接アクセスし、RLS で守る。サーバー側の処理は Edge Function と pg_cron に置く |
| `cacheComponents` / `partialPrefetching`（PPR） | 使わない。静的出力と一緒に使うと、ビルドが失敗する |
| `generateStaticParams` のない動的ルート（`/routines/[id]`） | クエリ文字列（`?id=`）で渡す |
| サーバー側での認証チェック | 画面側でログイン状態を確認して移動させる。本当の守りは RLS |
| `next/image` の既定の最適化 | 使わない（画像はほぼ不要） |
| Windows でのビルド結果を直接アップロード | Next.js 16.4.3 の不具合で、プリフェッチ用のファイル名が壊れる。Cloudflare 側（Linux）でビルドする |

### 7.3 秘密情報の扱い
- 画面に入れてよいのは、Supabase の URL と公開キー（anon / publishable key）だけ。RLS が前提になる。
- service_role キーと VAPID の秘密鍵は、Edge Function（または Worker）の secrets にだけ置く。リポジトリにも静的ファイルにも含めない。
- `.env*` は Git の対象外にする。

## 8. 無料枠の制約と、実現性の確認結果（2026-11-04 時点）

### 8.1 Web Push の対応条件
| 端末 | 条件 | 注意点 |
| --- | --- | --- |
| iPhone / iPad | iOS / iPadOS 16.4 以降。**ホーム画面に追加した Web アプリでのみ** 通知を使える。許可を求めるのは、ボタンを押したときなど、ユーザーの操作の中だけ | 通知のボタン（actions）は使えない、という報告がある。許可を一度拒否すると、ホーム画面のアイコンを削除して追加し直さない限り、もう一度は求められないとされる。iOS 18.4 以降は Declarative Web Push にも対応している（将来の検討対象） |
| Android | Chrome などでは、ブラウザのままでも PWA でも通知を使える | 省電力の設定によっては、通知が遅れることがある |
| PC | Chrome・Edge・Firefox・Safari | 補助的な利用 |

- Web Push は「届くことが保証された」仕組みではない。そのため、アプリを開いたときに今日の予定と未記録の予定を必ず表示する（F-310）。

### 8.2 無料枠
| サービス | 主な無料枠 | このアプリでの見込み |
| --- | --- | --- |
| Supabase Free | DB 500MB、MAU 5万、通信量 5GB、Edge Function 月50万回、無料プロジェクトは2つまで、**1週間使われないと一時停止**、自動バックアップなし | 毎分の送信処理を呼ぶと月 約4.3万回で、枠内に収まる。データ量はルーティン10件を1年続けても数千行で、余裕がある |
| Cloudflare Pages | 静的配信。ビルド回数に月ごとの上限がある | 個人利用なら問題ない |
| Cloudflare Workers Free（第2案） | 1日10万リクエスト、CPU は1回10ms、Cron Trigger はアカウント全体で5つまで、外部へのリクエストは1回50件まで | 毎分の実行は1日1,440回で、回数は余裕がある。一方、CPU 10ms で暗号化と署名ができるかは検証が必要 |

### 8.3 定期実行の精度
- pg_cron も Cron Trigger も、最短で1分ごとに実行できる。そのため、通知は予定時刻から **最大で約1〜2分遅れる** ことを前提にする（通知の配送そのものの遅れは別にある）。
- 予定の作成と未実施の確定は、0:00 JST（UTC では前日の 15:00）に実行する。cron の時刻は UTC で書く点に注意する。

### 8.4 認証の注意点
- iPhone のホーム画面アプリと Safari は、保存領域（Cookie など）を共有しない。メール内のリンクでログインする方式では、Safari 側だけがログイン状態になる。そのため、**メールで届いた6桁のコードをアプリ内で入力する方式** を使う。
- Supabase の標準のメール送信は、送信できる数が少なく、送り先にも制限がある。個人での利用なら足りる見込みだが、Plan Mode で確認する。

### 8.5 一時停止への対策
- 無料プロジェクトは、1週間使われないと一時停止する。毎日アプリを使えば止まらないはずだが、pg_cron の実行が「利用」として数えられるかは未確認である。止まった場合は、ダッシュボードから再開できる。

### 10.1 完成条件（課題の完成ライン）
1. メールの6桁コードでログインでき、別のユーザーのデータを読み書きできないことを、テストで確認している。
2. ルーティンを編集しても、過去の予定・実績・版が変わらない。変更履歴で前の設定を確認できる。
3. 曜日の設定どおりに、今日と明日の予定が重複なく作られる。0:00 JST をまたぐケースも単体テストで確認している。
4. 完了・延期・見送り・翌日以降の実施・未実施の自動確定を記録でき、予定時刻・通知時刻・実行時刻がそれぞれ別に保存される。
5. iPhone（ホーム画面アプリ）と Android の実機で、予定時刻と再通知の時刻に通知が届く。タップすると記録画面が開く。同じ通知が二重に届かない。
6. 日別・曜日別・時間帯別の達成率と遅延の傾向を表示できる。件数が少ないときは「参考値」と表示される。
7. 改善提案を少なくとも2種類表示でき、承認したときだけ新しい版が作られる。
8. 有料サービスを使わず、Supabase と Cloudflare の無料枠だけで動いている。
9. 秘密鍵がリポジトリと静的ファイルに含まれていない。
10. README に、公開URL・技術構成・通知の対応条件（iPhone はホーム画面への追加が必要）・無料枠の制約を記載している。
