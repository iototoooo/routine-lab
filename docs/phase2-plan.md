## 2. しくみ：予定の状態から通知ジョブを決める（1か所で行う）
**予定（`occurrences`）が作られる・変わるたびに、DB のトリガーがその予定の通知ジョブを合わせる。**
Phase 1 の7つの関数（作成・編集・アーカイブ・完了・延期・見送り・未実施の確定）をそれぞれ書き換えずに済み、今後どの経路で予定が変わっても通知がずれない。

| 予定の状態 | あるべき通知ジョブ |
| --- | --- |
| 予定どおり（`scheduled`） | 予定時刻の `initial` ジョブ1つ（期限：予定時刻＋60分）。予定時刻が変わったら（編集）古いジョブを取り消して作り直す |
| 延期中（`postponed`） | `next_remind_at` の `snooze` ジョブ1つ（期限：再通知時刻＋60分）。まだ送っていない `initial` と、時刻の違う `snooze` は取り消す |
| 通知済み（`notified`） | 新しいジョブは作らない（送信済みの記録は残す） |
| 完了・見送り・未実施・取り消し | 送っていないジョブ（`pending`）をすべて取り消す（`cancelled`） |

- 基準の時刻は、予定の `updated_at`（Phase 1 の関数が「今」を入れている）。すでに期限（＋60分）を過ぎた通知は作らない。
- 同じ予定・種類・時刻のジョブが「取り消し」で残っている場合は、それを「送信待ち」に戻す（例：21:00 → 20:00 → 21:00 と延期し直す）。一意制約のまま重複しない。
- `claim_due_jobs` でも、送る直前に予定の状態を確かめ、確定済みの予定・時刻がずれた再通知は送らずに取り消す（二重の守り）。
- 通知が1台以上に届いたら（Push サービスが 2xx を返したら）、`initial` の場合は予定を「通知済み」にし、イベント `notified` を残す（`finish_job` を更新）。
- **反映時の作成**：反映の時点で未来にある予定（今日・明日のうち、まだ予定時刻を過ぎていないもの、延期中のもの）にもジョブを作る。反映した直後から、実際の予定に通知が届き始める。

## 9. 判断していただきたいこと
| # | 内容 | 推奨 |
| --- | --- | --- |
| 1 | 反映した時点で、すでにある未来の予定にも通知ジョブを作るか | **作る**（作らないと、反映した日の予定には通知が来ない） |
| 2 | 「通知済み」にする条件 | **1台以上の端末に届いた（Push サービスが受け付けた）とき**。全部失敗したら「予定どおり」のまま（アプリを開けば見える） |
| 3 | 送信に失敗したとき（Push サービスの 5xx や通信エラー） | **期限（＋60分）までに最大3回まで、次の分に再送**。404/410 は再送せず端末を無効にする |
| 4 | 通知の期限 | 要件の例どおり、**予定時刻（再通知時刻）から60分** |
| 5 | 再通知の文面 | タイトルに「（再通知）」を付け、本文に延期回数を入れる |
| 6 | 本番 DB のスモークテスト | Phase 1 と同じ方式（必ず全体を取り消す）で行う |

### 判断事項の結論（2026-11-08 承認）
1. 反映時点の未来の予定にも作る。ただし通知時刻（予定時刻・再通知時刻）を過ぎた予定には新しく作らない。
2. 1台以上の Push サービスが受け付けたら「通知済み」。受け付けは端末での表示成功とは区別する。
3. 5xx・429・通信エラーだけのときは、期限内で最大3回再試行（最初の送信と合わせて最大4回）。404/410 は端末を無効にして再試行しない。
4. 期限は通知時刻から60分。
5. 再通知のタイトルに「（再通知）」、本文に延期回数。
6. 本番スモークは ROLLBACK 方式。本番での実行は別途承認。

### 計画から補った点・変えた点
- **通知ジョブに列を2つ追加**（計画では「新しい列なし」）：取り消しの理由と時刻を、後の分析で使えるように残すため（追加確認6）。
- **Phase 1 の不具合の修正**：同じ日の予定を2回編集すると、1回目の編集で残した `edited` イベントのせいで2回目が予定に反映されなかった（通知も古い時刻のままになる）。要件 4.2 の「まだ通知も記録もされていない予定は作り直す」に合わせ、`edited` 以外のイベントがある予定だけを残すように改めた。
- **Topic の切り詰め**：Push サービスの Topic は32文字までで、予定 ID（36文字）をそのまま渡すと末尾が切れていた。予定の通知ではハイフンを除いて渡す（test の通知は従来どおり）。
- 停止した送信（5分以上 `sending`）の回収は Phase 0 のまま（3回で failed）。送信の直後に落ちた場合は、同じ通知がもう一度届くことがある（端末上は同じ `tag` で置き換わる）。
